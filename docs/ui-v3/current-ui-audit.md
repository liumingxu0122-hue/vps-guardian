## 已确认的根因

### P0：当前导航文字“消失”

文字没有从 DOM 删除。当前选中项仍有 `aria-current="page"`，实测宽度为
200px；根因是浅色主题只覆盖选中背景，没有覆盖从深色主题继承的近白色文字：

```css
.primary-nav a.active {
  color: #eef2f5;
  background: #19201f;
}
```

浅色主题把背景改成近白的浅绿色后，文字和图标仍为 `rgb(238, 242, 245)`，
形成近乎不可见的前景。该问题必须用共享选中态 Token 修复，并增加每个路由的
可见性、对比度和 `aria-current` 回归测试。

### 双滚动

导航使用 `overflow-y: auto`。低高度实测 `scrollHeight=820`、
`clientHeight` 小于内容高度，同时页面本身也滚动，形成两个相邻的垂直滚动
容器。V3 应由 App Shell 明确分配滚动责任，桌面导航仅在低高度时提供单一、
可预期的内部滚动；手机 Drawer 打开时锁定背景滚动。

### Services 状态语义

Controller 当前用来源类型直接决定状态：

```python
"failed" if kind == "systemd_failed" else "observed"
```

这会把“检查已成功执行且未发现失败 unit”错误显示为失败。状态必须由结构化
解析结果决定，并区分执行失败、对象异常、空异常集合、无数据和解析失败。

### Incidents 选中态

当前选中行背景为 `rgb(17, 22, 26)`，详情区域也使用接近纯黑背景；浅色主题
中的部分文字没有切换为反色，导致严重对比度问题。V3 必须使用轻量 Accent
背景、内侧强调线和高对比文字，详情使用标准 surface Drawer。

## 阶段 1 原型验收门槛

进入真实 API 接入前，必须通过以下内部检查：

- 所有路由的选中导航文字可见、对比度合格，并保留 `aria-current="page"`。
- Services 主视图是高密度结构化列表，不是重复卡片墙。
- 原始证据默认关闭，页面不存在嵌套的小型滚动容器。
- “0 个失败 systemd unit”显示 Healthy，而不是 Failed。
- Incidents 选中行没有黑底，详情使用标准 surface Drawer。
- 中文原型没有随机英文句子。
- 390px 视口没有页面级横向溢出。
- 浅色、深色主题均有明确视觉层级。
- 原型不只是换色、圆角或 Skeleton。

阶段 1 不修改真实 Staging 数据，不把 fixture 引入生产数据路径，也不部署。
